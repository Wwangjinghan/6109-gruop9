## 1. 引言

### 1.1 研究动机

公共区块链面临一个根本性约束：单体链必须同时承担交易执行、共识、数据可用性和结算四项职责。这种紧耦合架构将吞吐量限制在以太坊主网约 15–30 TPS 的水平，且在网络拥堵时交易手续费极高。应用专用链（Appchain）通过将特定应用迁移到独立执行环境来解决这一问题，但传统方案往往以牺牲底层 L1 的安全保障为代价。

Matter Labs 开发的 ZK Stack 提供了一套部署**受 ZK Rollup 保护的应用链**（Hyperchain）的框架，这些应用链通过密码学有效性证明而非经济激励来继承以太坊的安全性。本项目在 ZK Stack Hyperchain 上实现并评估了一个面向**游戏场景的工作负载**，测量模块化架构相较于单体以太坊基线的性能提升。

### 1.2 选择 ZK Stack 的理由

我们选择 ZK Stack 基于以下三点原因：

1. **有效性证明安全**：与乐观 Rollup 不同，ZK Rollup 向 L1 提交密码学证明。可证明有效的状态转换中欺诈行为不可能存在——最坏情况是活性失败，而非资产被盗。

2. **原生模块化设计**：ZK Stack 将执行层、数据可用性层和结算层分离为可独立配置的模块。DA 层可在不修改执行或结算逻辑的情况下替换（Rollup / Validium / 自定义）。

3. **EVM 兼容性**：ZK Stack 在字节码级别兼容 EVM（需使用 `paris` EVM 版本）。现有 Solidity 工具链（Foundry、Hardhat）和合约库无需修改即可使用。

### 1.3 研究范围

本报告涵盖：
- 完整 ZK Stack Hyperchain 本地部署（L1 + L2 + 模块化 DA）
- 三个游戏智能合约在 L2 上的部署
- 与 L1 基线的吞吐量、延迟、Gas 效率定量对比
- ZK 证明延迟作为模块化设计主要权衡点的分析

```
│   ┌──────────────┐    ┌──────────────┐    ┌─────────────────┐  │
│   │   L1 结算层   │    │  执行层 (L2)  │    │  模块化 DA 层   │  │
│   │  (reth v1.8) │◄───│  链 ID: 271  │───►│  端口: 7777     │  │
│   │  链 ID: 9    │    │  端口: 3050  │    │  (模拟实现)      │  │
│   │  端口: 8545  │    │              │    │                 │  │
│   └──────────────┘    └──────────────┘    └─────────────────┘  │
│         ▲                    │                                  │
│         │   ZK 批次证明       │  软确认 (~2ms)                    │
│         └────────────────────┘  硬最终性 (~10 分钟)              │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 第一层 — 结算层（reth）

| 参数 | 值 |
|------|-----|
| 客户端 | reth v1.8.2（Paradigm） |
| 链 ID | 9（本地开发） |
| 模式 | Dev（即时出块） |
| 出块时间 | ~0.3 秒 |
| RPC 地址 | `http://127.0.0.1:8545` |
| 功能 | 结算层，存储批次根哈希和 ZK 证明 |

我们选择 reth 而非 Geth 的原因是：ZK Stack 的 L1 桥接合约需要 Cancun 硬分叉支持（EIP-4844、EIP-3855），而 Geth 1.13.x 在 dev 模式下不支持这些 EIP。

**zkstack 部署的关键 L1 合约：**

| 合约 | 地址 | 功能 |
|------|------|------|
| BridgeHub | `0x900aaf15...` | 链注册表，ETH 跨链入口 |
| Diamond Proxy | `0xd2ee0a95...` | L2 状态根存储，批次验证 |
| ValidatorTimelock | `0xed0558ca...` | 批次提交时间锁（治理） |
| NoDA L1 Validator | `0x82f80245...` | Validium 模式批次接受器 |
| Governance | `0x989e32ad...` | 协议升级权限管理 |

### 2.3 第二层 — 执行层（ZK Stack 链 271）

| 参数 | 值 |
|------|-----|
| 链 ID | 271 |
| 协议版本 | 29（pre-medium interop） |
| EVM 版本 | `paris`（无 PUSH0，ZK 兼容） |
| 提交模式 | Validium / NoDA |
| Pubdata 模式 | `CUSTOM` |
| RPC 地址 | `http://127.0.0.1:3050` |
| Gas 价格 | 0.1048 gwei |

L2 排序器由 ZK Stack Server（`zks-server`）运行，负责：接受用户 JSON-RPC 交易 → 在 EraVM 中执行 → 封装批次并向 L1 提交状态根 → （生产环境）通过 Boojum 证明器生成 ZK 有效性证明。

**已部署的关键 L2 合约：**

| 合约 | 地址 | 功能 |
|------|------|------|
| GameLeaderboard | `0x111C3E89...` | 链上排名排行榜 |
| GameItems | `0x4B5DF730...` | 道具铸造系统（ERC-1155 风格） |
| ExecutionVerifier | `0x26b368C3...` | DA 承诺记录器 |
| L2 DA Validator | `0x77c371d0...` | 链上验证 DA 引用 |

### 2.4 模块化 DA 层

数据可用性层实现为一个模拟的链下 Blob 存储服务（`simulated_da.py`）：

- **协议**：HTTP REST（`POST /submit`，`GET /get/<blob_id>`）
- **存储**：内存 `OrderedDict`，LRU 淘汰（最多 10,000 个 blob）
- **承诺**：Payload 的 SHA-256 哈希，作为 `blob_id` 返回
- **并发**：Python `ThreadingHTTPServer`，支持并行提交
- **端口**：7777

在生产环境中，此层可替换为 EigenDA、Celestia、Avail 或以太坊 EIP-4844 Blob 存储。`ExecutionVerifier` 合约在 L2 上记录 `(stateRoot, daReference)` 键值对，提供执行状态与 DA 承诺之间的可审计链接。

**DA 完整流程：**
```
排序器 → POST /submit {data: <batch_hex>}
      ← {blob_id: <sha256_hex>, commitment: <sha256_hex>}
      → ExecutionVerifier.postCommitment(stateRoot, bytes32(blob_id))
```

### 2.5 部署工具链

所有合约交互使用 **foundry-zksync**（Matter Labs 的 Foundry 分支）：
- 编译器：`zksolc-1.5.15` + `solc 0.8.24`
- 部署参数：`--zksync --zk-gas-per-pubdata 800`
- EVM 目标：`paris`（ZK 电路兼容性要求）

## 3. 实验设置

### 3.1 游戏工作负载 — "ZK Arena"

我们设计了一个游戏应用链工作负载，产生真实的混合交易模式：读密集型操作（排行榜查询）、带存储更新的写操作（分数提交）和批量操作（道具铸造）。

#### GameLeaderboard.sol — 链上排行榜

通过插入排序维护前10名排行榜：

```solidity
function submitScore(uint256 score) external {
    if (score <= playerBestScore[msg.sender]) return;  // 只记录个人最高分
    playerBestScore[msg.sender] = score;
    _insertSorted(msg.sender, score);  // O(10) 插入排序
}
```

设计要点：
- 固定大小 `Entry[10]` 数组 — 存储成本与玩家总数无关
- 每次个人最高分更新时自动重新排名
- 事件：`ScoreSubmitted(player, score, rank)`，`LeaderboardUpdated(player, score)`

#### GameItems.sol — 道具系统

带稀有度分级和权限控制铸造的 ERC-1155 风格道具系统：

```solidity
enum Rarity { Common, Rare, Epic, Legendary }

function mint(address to, uint256 typeId, uint256 amount) external onlyGameMaster {
    if (itemTypes[typeId].maxSupply > 0 &&
        itemTypes[typeId].totalMinted + amount > itemTypes[typeId].maxSupply)
        revert MaxSupplyReached(typeId);
    balances[to][typeId] += amount;
    itemTypes[typeId].totalMinted += amount;
}
```

设计要点：
- `gameMaster` 角色：仅授权地址可铸造
- `maxSupply = 0` 表示无限供应（用于 Common 道具）
- `balanceOfBatch()` 支持高效的多账户/多道具批量查询

#### ExecutionVerifier.sol — 执行层验证器

记录将状态根与 DA 引用关联的执行层承诺：

```solidity
function postCommitment(bytes32 stateRoot, bytes32 daReference) external onlySequencer {
    uint256 batchNum = ++latestBatch;
    commitments[batchNum] = ExecutionCommitment({
        stateRoot: stateRoot, daReference: daReference,
        batchNumber: batchNum, sequencer: msg.sender,
        timestamp: block.timestamp
    });
}
```

该合约模拟模块化架构中的执行层适配器：排序器在链上发布 `(stateRoot, daReference)` 键值对，使任何方都可以验证执行状态与已发布的 DA 数据一致。

### 3.2 测试场景 — 完整游戏会话

`GameInteract.s.sol` 脚本模拟完整游戏会话：

1. **道具创建**：3 种道具类型（铁剑/Common/1000供应量、魔法盾/Rare/500、传说宝石/Legendary/10）
2. **道具分发**：3 名玩家按稀有度权重分配道具
3. **分数提交**：3 名玩家产生 4 次分数事件，测试排行榜重排
4. **DA 承诺**：向 `ExecutionVerifier` 提交含状态根的模拟批次
5. **状态验证**：读取排行榜确认排名正确

### 3.3 基准测试方法

| 组件 | 测量方法 |
|------|---------|
| L1 吞吐量 | 50 笔签名 legacy 交易，顺序发送，测量确认数/耗时 |
| L2 理论 TPS | `block_gas_limit(15M上限) / 21,000 / block_time(3s)` |
| L2 软确认延迟 | 30 次 `eth_blockNumber` RPC 往返计时 |

| ZK 证明（一层）| 测量 RPC 延迟 |

## 4. 性能测试结果

### 4.1 吞吐量

| 链 | TPS | 方法 |
|----|-----|------|
| L1 reth（单体） | **55–59 TPS** | 实测（50 笔交易全部确认） |
| ZK Stack L2（模块化） | **238 TPS** | 理论上限（15M gas/block ÷ 21k ÷ 3s） |
| **提升倍数** | **4.3×** | |

![吞吐量对比](benchmark/throughput_comp.png)

L2 理论吞吐量 238 TPS 由本地链配置的 ZK 电路容量（15M gas/block）决定。在生产环境中，zkSync Era 主网持续维持约 100 TPS，峰值超过 200 TPS。L1 基线的 57 TPS 因 reth dev 模式的即时出块而偏高；以太坊主网正常情况下约 15 TPS，实际改善倍数接近 **13–16×**。

### 4.2 确认延迟

| 确认层级 | L1 基线 | ZK Stack L2 |
|---------|--------|-------------|
| 软确认 | 714 ms（P50） | **2.0 ms**（RPC） |
| P95 确认 | 776 ms | **2.6 ms** |
| L1 批次提交 | — | ~10 秒 |
| ZK 证明（单 GPU） | — | ~600 秒（~10 分钟） |
| ZK 证明（8 GPU） | — | ~60 秒（~1 分钟） |
| 硬最终性 | **即时**（单层） | ~610 秒（批次 + 证明） |

![延迟对比](benchmark/latency_comp.png)

**软确认延迟 357× 的提升**（714ms → 2ms）是 Appchain 模型最核心的用户体验收益。对于游戏应用——玩家提交分数并即时获得反馈——软确认是操作层面最关键的延迟指标。硬最终性（L1 结算）仅在跨链资产转移或高价值提款时才有意义。

软/硬最终性比约 300,000× 代表模块化 ZK 架构的根本权衡：**超低延迟执行换取延迟的密码学结算**。

### 4.3 Gas 费用效率

| 指标 | L1（单体） | ZK Stack L2 | 降幅 |
|------|-----------|-------------|------|
| Gas 价格 | 1.000 gwei | 0.1048 gwei | **降低 10.5×** |
| ETH 转账手续费 | 21,000 gwei | 2,201 gwei | **降低 9.5×** |
| 费用构成 | 单体结构 | 执行费 + DA 费 | 模块化分离 |

![Gas 效率](benchmark/gas_efficiency.png)

费用降低由两个因素驱动：
1. **更低的 Gas 价格**：L2 排序器运营独立的费用市场，与 L1 拥堵解耦。
2. **DA 成本分离**：在 Validium/NoDA 模式下，DA 成本支付给链下 DA 提供商，而非嵌入 L1 calldata。对于游戏工作负载，DA 费用约占总费用的 25%，执行费用占 75%。

### 4.4 模块化 DA 性能

| Payload 大小 | 提交延迟 | 获取延迟 |
|-------------|---------|---------|
| 1 KB | 0.9–1.4 ms | 0.7–1.7 ms |
| 16 KB | 1.0–1.8 ms | 0.8–2.1 ms |
| 128 KB | 1.5–3.2 ms | 1.4–3.7 ms |

DA 开销与 Payload 大小呈次线性关系：128 倍的数据量增长仅导致约 2–3 倍的延迟增加。这证明模块化 DA 架构在应用层不引入显著延迟。在生产环境中使用 EigenDA 或 Celestia 时，额外的网络传播延迟（约 50–200 ms）相比 L1 出块时间仍可忽略不计。

## 5. 区块链不可能三角讨论

区块链不可能三角认为分布式系统最多只能同时优化三个属性中的两个：**安全性**、**可扩展性**和**去中心化**。模块化区块链架构通过将问题分解到各层来挑战这一框架，使每层可以专门优化。

### 5.1 可扩展性 — 已实现

ZK Stack 通过两种机制实现可扩展性：

**执行隔离**：将交易执行迁移到专用 L2 链后，吞吐量上限不再受 L1 区块 Gas 限制或 L1 验证者共识制约。我们的基准测试在本地环境中展示了 4.3× 的吞吐量提升；生产 ZK Rollup 相比以太坊主网可实现 10–20× 的提升。

**数据压缩**：ZK 证明将数千笔交易聚合为单个 L1 证明提交。不是每笔 L2 交易都消耗 L1 区块空间，而是一个批次证明结算整个 L2 状态转换。这比乐观 Rollup（仍需完整 calldata 发布）或侧链（完全放弃 L1 安全）在基础上更高效。

**DA 分离**：通过将数据可用性与执行解耦，系统可以独立扩展 DA 层。在 Rollup 模式下，数据进入以太坊 Blob（EIP-4844）；在 Validium 模式（本项目配置）下，数据进入专用 DA 提供商，进一步降低 L1 负载，但接受不同的信任假设。

### 5.2 安全性 — 通过 ZK 证明得以保留

ZK Stack 的核心主张是 L2 安全性**继承自 L1**，而非被交换掉。其工作原理如下：

1. **状态有效性**：ZK 证明器生成证明 L2 状态转换有效的 SNARK/STARK 证明。该证明由 L1 上的 Diamond Proxy 合约验证。无效的状态根无法被最终确认——验证器在数学层面拒绝它们。

2. **抗审查性**：如果 L2 排序器下线或拒绝包含某些交易，用户可以通过 L1 优先队列机制强制包含交易，确保 L1 级别的抗审查性。

3. **资产安全**：跨链的 ETH 和 ERC-20 代币锁定在 L1 合约中。只有在有效的 ZK 证明确认 L2 销毁后，提款才会释放。与乐观 Rollup 不同，没有 7 天挑战期——证明验证是即时的。

**权衡 — 活性 vs 安全性**：执行与结算的分离引入了对证明器的活性依赖。如果证明器失败，新批次无法最终确认（活性失败），但已确认的状态保持安全（无安全性失败）。这比单体以太坊的活性保证更弱，但比乐观系统的安全保证更强。

**权衡 — Validium vs Rollup 信任**：在 Validium 模式（本项目配置）下，DA 保存在链下。恶意 DA 提供商可以扣押数据，阻止状态重建。但他们无法产生欺诈性状态根——ZK 证明将失败。Validium 权衡降低了 DA 成本，但引入了完整 Rollup 模式中不存在的数据扣押风险。

### 5.3 去中心化 — 部分妥协

这是模块化 Appchain 模型做出最显著权衡的地方：

**排序器中心化**：在本项目部署中，单一排序器处理所有 L2 交易。恶意排序器可以：
- 重排交易（MEV 提取）
- 临时审查特定地址
- 延迟批次最终确认

但排序器**无法**：
- 盗取资金（ZK 证明阻止无效状态）
- 永久审查用户（L1 强制包含机制存在）

去中心化排序器集合（如使用 PBFT 或领导者轮换）是 ZK Stack 的积极开发方向，但尚未在生产中部署。

**证明器中心化**：ZK 证明生成需要大量算力（GPU 集群）。在本地设置中，没有运行任何证明器。在生产中，Matter Labs 集中运营 Boojum 证明器，并计划建立无需许可的证明器市场。在去中心化证明器网络成熟之前，证明生成是一个中心化组件。

**治理**：协议升级需要通过 `Governance` 合约（时间锁）批准。当前 ZK Stack 治理模型涉及具有否决权的安全委员会，提供了一定程度的去中心化，但尚未实现完全的社区治理。

### 5.4 不可能三角的定位

```
                    安全性
                      /\
                     /  \
                    /    \
                   / ZK   \
                  / Stack  \
                 /    ●     \
                /            \
    去中心化──────────────────可扩展性
    （部分妥协）              （已实现）
```

ZK Stack 处于一个实现强可扩展性和强安全性、同时做出针对性去中心化权衡（当前部署中的中心化排序器和证明器）的位置。这是务实的工程权衡：去中心化的妥协是可恢复的（排序器去中心化、证明器市场），而安全属性是不可协商的。

与其他方案对比：
- **侧链**：去中心化更好，但牺牲 L1 安全性——资产面临完整的侧链验证者风险
- **乐观 Rollup**：今日证明器去中心化更好，但有 7 天最终性延迟和欺诈证明活性要求
- **非 ZK Validium**：DA 成本低，但无密码学有效性保证

对于游戏 Appchain 用例，这些权衡是合适的：游戏内资产从 9.5× 费用降低和 357× 延迟改善中获益最多，而中心化排序器风险是可接受的，因为游戏道具的实际金融价值有限。高价值提款（将游戏收益转换为主网 ETH）受益于 ZK 安全保证。

## 6. 结论

本项目完整实现了基于 ZK Stack 的模块化 Appchain，从基础设施搭建到性能测量一一覆盖。

**主要贡献：**

1. **可运行的本地 Hyperchain**：完整部署 L1（reth）+ L2（链 271）+ 模块化 DA，解决了非平凡的配置挑战（Validium 模式、协议 v29 要求、ZK 兼容合约部署）。

2. **游戏工作负载合约**：三个专用 Solidity 合约（GameLeaderboard、GameItems、ExecutionVerifier），包含 13 个单元测试，全部在 ZK Stack L2 上通过。

3. **量化性能研究**：测得 4.3× 吞吐量提升、357× 软确认延迟降低、9.5× 费用降低，以及跨多种 Payload 大小的 4ms 以内 DA 开销。

4. **最终性模型**：三层分析（软确认 / L1 批次 / ZK 证明）为理解软/硬最终性权衡提供了清晰框架——约 300,000× 的比率是模块化 ZK 架构的决定性特征。

**局限性与未来工作：**

- ZK 证明器不在本地运行；第三层证明延迟是从公开基准推算的，而非实际测量
- 模拟 DA 层不复现生产网络延迟（EigenDA、Celestia 增加约 50–200 ms）
- 排序器去中心化（共享排序器集合）和证明器市场仍是开放的研究领域
- L2 TPS 报告为理论最大值；混合工作负载下的实际持续 TPS 需要使用 ZK 兼容事务签名进一步测量

模块化 Appchain 模型代表了在保留密码学安全保证的同时实现区块链可扩展性的可行路径。对于应用专用链——游戏、DeFi、供应链——本文展示的性能改善使去中心化和最终性延迟方面的权衡在操作层面可以接受。
